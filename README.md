# H3 VRAM Master for ComfyUI

**H3VM = H3 VRAM Master**

**中文** | [English](README_EN.md)

H3 VRAM Master 是为 **MiniMax H3 本地生成**设计的显存与多显卡计算管理器。

它不是单纯的“双卡 Loader”，也不是为了让第二张显卡亮起来而存在。

它真正要解决的是：

> **让整台电脑的 GPU、显存和系统内存一起服务 H3，并根据当前硬件与任务，选择最合适的执行方式。**

普通工作流主要负责“生成什么”。

H3VM 负责“这个模型应该怎样放、怎样拆、怎样传、怎样让一张或多张显卡把它跑完”。

> **你负责选镜头，H3VM 负责安排显卡。**

当前稳定版：**v0.20.0-rc6**

---

## 为什么需要 H3VM？

本地 H3 很多时候不是没有算力，而是算力没有被有效组织起来：

- 一张显卡满载，另一张几乎闲着；
- 两张卡显存很多，但模型还是只能塞进一张；
- 为了双卡而双卡，搬运成本反而超过计算收益；
- Windows 没有 NVLink / CUDA P2P，传统多卡路线失效；
- 双 16GB 与 16GB + 8GB 明明是不同机器，却被迫套同一组参数。

H3VM 不要求两张显卡必须完全相同，也不把 NVLink 当作前提。

它更关心：

> **你现在这台机器，怎样跑才最划算。**

## 当前稳定版的运行模式

### 单卡模式

只使用主 GPU。适合作为质量、性能和显存基线。

内部名：`SINGLE_GPU`

### 双卡协同

日常推荐路线。两张卡共同承担部分 H3 计算，在速度、显存压力与稳定性之间取得平衡。

内部名：`DUAL_QUIET`

### 双卡扩容

优先解决“单卡跑不下”的问题。通过 RAM backing、QKV / MLP 分工、动态显存驻留等方式降低单卡峰值显存。

内部名：`DUAL_CAPACITY`

### 双卡极速

速度优先的 Mode4 / FullThrottle 路线。允许 Snapshot / Predictor 等近似执行，让主卡和副卡尽可能错位推进不同阶段。

内部名：`DUAL_SYNC_ACCEL`

> 开发线中的“**双卡原生** / Exact-SP”属于下一阶段精确双卡路线，只有经过真实 H3 parity、wall time、VRAM 与 transport 门禁后才会晋升为稳定公开模式。

---

## 没有 NVLink，也可以双卡

普通消费级 Windows 双卡没有 CUDA P2P，不应被当作边缘场景。

H3VM 会在可用时利用显卡直连；无法直连时，通过 Host/RAM Relay 完成卡间数据交换。

长期目标不是让用户研究 PCIe 拓扑，而是：

> **能直连就直连，不能直连就绕路，但尽量别堵车。**

---

## H3VM 不只管理“多卡”，也管理显存

H3VM 的长期职责包括：

- 模型与权重什么时候进入显存；
- 哪些数据值得驻留、哪些可以放在系统内存；
- 主卡和副卡分别承担多少计算；
- 两张卡之间怎样传数据；
- 量化权重怎样只计算当前需要的部分；
- Video VAE 怎样分担；
- 新优化何时应该启用，失败时怎样自动回退。

所以它真正解决的问题不是“怎么用两张卡”，而是：

> **整台电脑的 GPU 和内存，怎样一起服务 H3？**

## 两种使用方式

### H3VM Master Loader

一体化主控，适合直接生成和快速 A/B。

### H3VM Core

用于已有复杂工作流的快速接入：

```text
原 MODEL
   |
   v
H3VM Core
   |
   v
原工作流
```

Core 负责 GPU / 显存 / 执行调度，不修改 Prompt、Seed、分辨率、Sampler、Sigmas 或实际采样步数。

目标是：

> **不需要为了多卡重做整个工作流。**

## 开发总指导思想

H3VM 不追求收集最多的多 GPU 技术名词。

任何新技术进入主线，都至少应该带来一种真实、可测量的正收益：

1. **速度收益**：更短的实际 wall time；
2. **容量收益**：单卡 OOM，多卡能够完成；
3. **质量 / 精确性收益**：相同成本下更可靠；
4. **兼容性收益**：更多普通硬件能够工作；
5. **使用成本收益**：更少改工作流、更少手调、更容易理解和复现。

**GPU1 更忙，不等于优化成功。**

完整的长期产品与开发总纲：

> [H3VM_PRODUCT_CHARTER.md](H3VM_PRODUCT_CHARTER.md)

技术每天都可以更新，这个方向不能跟着术语漂。

---

## 智能调度，而不是永久手调参数

H3VM 的长期方向不是越来越多固定比例，而是一个越来越懂硬件的 Planner。

它应该逐步综合：

- VRAM 容量；
- GPU 计算规模；
- 两张卡是否接近对称；
- CUDA P2P 是否可用；
- Host Relay 实测带宽；
- 模型与量化格式；
- 分辨率、时长与步数；
- 当前目标是速度、容量还是精确性。

然后决定怎么分工。

> **不是让用户学会调多卡，而是让 H3VM 学会用户的电脑。**

## 安装

1. 将插件目录放入 `ComfyUI/custom_nodes/`。
2. 安装 `requirements.txt` 中缺少的依赖。
3. 确保目标 GPU 都对当前 ComfyUI / Python 进程可见。
4. 重启 ComfyUI。

覆盖升级时建议先移走旧 H3VM 插件目录，避免重复节点和运行时桥冲突。

同型号显卡完全可以使用；H3VM 判断的是不同 CUDA 逻辑设备，而不是显卡名称。

Windows 下如果当前进程只暴露一张显卡，请先确认 `cuda:0` 与 `cuda:1` 是否都真正可见。

---

## 推荐测试方式

比较不同模式时，请尽量保持 Prompt、Seed、模型、LoRA、分辨率等条件一致。

对性能模式，主要看 **wall time 与主卡关键路径**。

对扩容模式，成功标准首先是：

> **单卡跑不了，多卡能完成。**

不同 GPU 组合的日志、显存峰值和真实生成时间都非常有价值。

## 项目边界

公开 H3VM 聚焦底层执行：VRAM 管理、多 GPU 计算、Planner、Host Relay、Attention / QKV / MLP 分片、Capacity、Mode4、Exact-SP 研究、Dual Video VAE 与 telemetry。

任务队列、Worker Lease、工程生命周期、P1/P2/P3 调度、Artifact 路由等上层生产系统不属于 H3VM 公共运行时。
